01Definition of cloud computing

Cloud computing is the on-demand delivery of computing resources (servers, storage, databases, networking, software) over the internet, paid for as they are used instead of bought and maintained up front.

NIST definition (memorise this line)

"A model for enabling ubiquitous, convenient, on-demand network access to a shared pool of configurable computing resources that can be rapidly provisioned and released with minimal management effort."

The five essential characteristics (NIST)

CharacteristicMeaningExample
On-demand self-serviceProvision servers or storage yourself through a console or API, no human interaction with the providerLaunching an EC2 VM from the AWS console in minutes
Broad network accessServices reachable over the network from any standard deviceLaptop, phone, or another cloud service calling the same API
Resource poolingProvider's physical resources shared among many customers (multi-tenancy), assigned dynamically; customer knows the region, not the exact machineHundreds of VMs on one physical host
Rapid elasticityCapacity grows and shrinks automatically with demand; appears unlimited10 servers at night, 500 during a sale, back to 10 by evening
Measured serviceUsage (CPU-hours, GB stored, requests) is metered and billed like electricityPay per GB-month on S3, per request on Lambda

The economic shift is from CapEx to OpEx: no large upfront purchase of hardware, only operational payment for what is used. This is what lets a start-up deploy in Mumbai, Frankfurt and Virginia in one afternoon.

Cloud
The provider's data centres plus the software that rents slices of them.
Utility computing
Computing consumed like electricity: metered, elastic, always available.
Multi-tenancy
Many customers sharing the same physical hardware with logical isolation.

02Evolution of cloud computing

  • Mainframe (1950s–60s) - one large central machine shared through dumb terminals. First idea of computing as a shared utility.
  • Client-server (1980s) - cheap PCs (clients) request services from a central server over a LAN.
  • Cluster and grid (1990s) - many independent machines connected to act as one: inside one site (cluster), then across organisations (grid).
  • Virtualization (2000s) - a hypervisor lets one physical server run several isolated VMs. Resources can be carved up, moved, copied and billed.
  • Cloud (2006 onward) - Amazon launches EC2/S3, turning virtualized data centres into a rentable public service. Later: containers, serverless, edge.

03Parallel vs distributed computing

A cloud data centre is a distributed system whose individual nodes are parallel machines. Both foundations appear in every exam.

AspectParallel computingDistributed computing
DefinitionMany processors work on parts of one task at the same timeMany independent computers cooperate over a network
MemoryUsually shared memory (all processors see the same RAM)Each node has its own private memory
CommunicationThrough shared memory, very fastThrough message passing, slower
CouplingTightly coupled, one machineLoosely coupled, many machines
ClockSingle system clockNo global clock; synchronisation is a real problem
FailureOne failure usually stops the whole jobDesigned to keep working when a node fails
ScalabilityLimited by cores in the machineScales by adding machines
Main goalSpeed up one computationResource sharing, availability, scale
ExampleMulti-core CPU, GPU, supercomputerInternet, Hadoop cluster, cloud data centre

04Underlying principles

Parallel computing

  • Task decomposition - split by data (data parallelism) or by work (task parallelism).
  • Concurrency and synchronisation - locks, barriers, semaphores prevent race conditions.
  • Flynn's taxonomy - SISD, SIMD (GPUs), MISD, MIMD (multi-core CPUs).
  • Amdahl's law - speed-up is limited by the serial fraction. If 10% must run sequentially, no number of processors gives more than 10x speed-up.
  • Load balancing - the slowest processor sets the finish time.

Distributed computing

  • Message passing - no shared memory; nodes cooperate via RPC, REST, MPI, queues.
  • Transparency - hide where resources live, how they are accessed, whether replicated, and when they move or fail.
  • No global clock - ordering needs Lamport / vector clocks or consensus (Paxos, Raft).
  • Fault tolerance - partial failure is normal; replication, heartbeats, retries.
  • CAP theorem - during a network partition, choose consistency or availability. Drives every distributed database design.
  • Architectural styles - client-server, peer-to-peer, three-tier, service-oriented / microservices.

05Cloud characteristics (innovative)

Beyond the NIST five, examiners expect this extended list:

  • Virtualization - the technical foundation; hardware abstracted into software units created and destroyed in seconds.
  • Pay-as-you-go - CapEx becomes OpEx; metering makes it real.
  • Reliability and availability - replication across zones/regions; SLAs of 99.9%+.
  • Global scale - deploy in many regions in an afternoon.
  • Automation and programmability - infrastructure as code (Terraform, CloudFormation), APIs everywhere.
  • Security as shared responsibility - provider secures the platform; customer secures data, identities, configuration.
  • Managed innovation - ML, analytics, serverless, managed databases consumed as building blocks.
One-line answer

Together these turn computing from a product you buy into a utility you consume.

06Elasticity in cloud

Elasticity is the ability to automatically acquire resources when demand rises and release them when it falls, so resources in use always match the workload. Scale out/in (more/fewer instances) or up/down (bigger/smaller instances), without downtime.

ScalabilityElasticity
MeaningCapacity to handle growing load by adding resourcesAutomatic scaling up and down in real time
DirectionUsually up only, often plannedBoth directions, driven by metrics (CPU, queue length)
ExampleBuying a bigger server for Diwali seasonAuto Scaling Group: 2 servers at night, 20 at peak, 2 after

Example: an e-commerce site keeps 2 web servers at night, grows to 20 when CPU crosses 70%, and shrinks back after the sale. The customer pays only for servers that ran.

07On-demand provisioning

Resources (VMs, storage, networks, databases, accounts) are allocated at the moment requested via portal or API, and de-allocated when no longer needed. Weeks of procurement become seconds.

User requests→Self-service portal / API→Provisioning engine→Resource ready

Types of provisioning

TypeIdeaSuitsExample
Advance (static)Fixed resources contracted in advance, flat feeSteady, predictable loadReserved Instances for a year
DynamicAdded/removed automatically as load changes, pay per useVariable trafficAuto Scaling policies
User self-provisioningCustomer creates resources directly with a credit card, in minutesDev/test, learningVM from the Azure portal

Provisioning by what is provisioned

  • Server - physical/virtual server with OS and software.
  • Storage - block, file, object storage with capacity and performance.
  • Network - IPs, subnets, firewalls, load balancers, VPNs.
  • Application/service - managed database, SaaS accounts for users.
  • User (identity) - accounts, roles, permissions via IAM.

Risk: uncontrolled self-provisioning causes cost sprawl and security gaps without governance policies.

★Case studies & scenarios

Try each one on paper first, then open the model answer.

Case 1 · Festival sale

An e-commerce site gets 10x traffic during a festival sale and near-zero traffic at night. It currently owns 20 servers sized for the peak. Identify the problem and design a cloud solution with elasticity and provisioning.

Model answer

Problem: static advance provisioning for the peak wastes money (18 servers idle most days) yet still risks under-provisioning if the sale exceeds estimates.

Solution: move to dynamic provisioning + elasticity: an Auto Scaling Group behind a load balancer, scaling on CPU/request-rate (e.g. add servers above 70% CPU). Keep 2 servers at night, grow to 20+ at peak, shrink after. Pay per server-hour (measured service).

Models: public cloud IaaS (EC2) for full control; hybrid if payment data must stay private.

Case 2 · Parallel or distributed?

Classify: (a) GPU training a neural network, (b) Google Search serving queries worldwide, (c) a Hadoop cluster counting word frequencies. Justify each.

Model answer
  • (a) Parallel: one machine, many cores, shared memory, single clock, goal is speed.
  • (b) Distributed: thousands of independent servers, private memories, message passing, no global clock, goal is availability and scale.
  • (c) Distributed with parallel nodes: cluster of machines (distributed) each using multi-core parallelism internally - exactly like a cloud data centre.
Case 3 · College lab on IaaS vs PaaS vs SaaS

A college wants: (a) student VMs for OS lab, (b) a platform for final-year projects in Python/Node without server management, (c) email for all staff. Map each to IaaS/PaaS/SaaS with an example.

Model answer
  • (a) IaaS (EC2 / Azure VMs): admins need OS-level control to install kernels and tools.
  • (b) PaaS (App Engine / Heroku / Elastic Beanstalk): students push code; provider manages runtime, scaling, patching.
  • (c) SaaS (Gmail / Microsoft 365): no installation, browser access, provider updates.
Case 4 · Elasticity vs scalability

A manager says "we are scalable because we bought a bigger server for next year". Explain why this is scalability but not elasticity, and what is missing.

Model answer

Buying a bigger server is scalability (capacity to grow, planned, one direction). Elasticity additionally needs automation + shrink-back: metrics-driven scale-out/in in real time with per-use billing. Missing: auto-scaling policies, monitoring, measured service, and the ability to release resources (and stop paying) when demand falls.

Case 5 · Hospital cloud choice

A hospital chain must keep patient records compliant and private, but wants cheap public-cloud burst capacity for appointment-booking traffic spikes. Recommend a deployment model.

Model answer

Hybrid cloud: sensitive records stay in a private cloud (control, compliance); the booking front-end bursts to the public cloud at peak. Connect with VPN/direct link and IAM federation. Pure public fails compliance; pure private cannot burst cheaply; multi-cloud adds unneeded complexity here.

Case 6 · VDI for exam labs

A university wants identical exam desktops on cheap lab PCs with no data left on the machines. Propose VDI: components, persistent vs non-persistent, pros/cons.

Model answer

Components: thin clients/laptops → connection broker (auth, assign desktop) → desktop VMs on hypervisor + central storage, over RDP/PCoIP display protocol.

Use non-persistent desktops from a golden image (fresh every session, nothing stored locally). Pros: central patching, data stays in data centre, any device works. Cons: network-dependent, upfront server/storage cost, licensing complexity (Horizon / Citrix / Azure Virtual Desktop).

12Quick revision (2-mark answers)

  • Cloud: on-demand network access to a shared pool of configurable resources, billed per use.
  • NIST 5: on-demand self-service, broad network access, resource pooling, rapid elasticity, measured service.
  • CapEx → OpEx: no upfront hardware purchase; pay operationally per use.
  • Evolution: mainframe → client-server → cluster/grid → virtualization → cloud (2006 EC2/S3).
  • Parallel: many processors, one machine, shared memory, goal is speed.
  • Distributed: many machines, private memories, message passing, goal is scale/availability.
  • Amdahl's law: serial fraction caps speed-up (10% serial → max 10x).
  • CAP: during partition choose consistency or availability.
  • Elasticity: automatic scale up and down with demand; scalability is growth only.
  • Provisioning: advance (fixed), dynamic (auto), self-service (portal/API).
  • IaaS: VMs/storage/network (EC2); PaaS: platform for code (Heroku); SaaS: ready app (Gmail).
  • Deployments: public, private, hybrid, community, multi-cloud.
  • VDI: desktops as central VMs; only pixels travel to endpoints.
  • DR: restore IT after disruption; RTO = how fast, RPO = how much data loss.
