01Service-oriented architecture (SOA)

SOA builds an application from independent, reusable services, each doing one business function. Services communicate over a network using standard protocols, so they can be written in different languages and run on different platforms.

RoleDoes what
ProviderCreates the service and publishes its description (WSDL).
RegistryDirectory (UDDI) where services are listed and discovered.
ConsumerFinds the service and calls it (bind + invoke).

Features: loose coupling, reusability, interoperability, abstraction, discoverability. Example: a travel site combining separate flight, hotel and payment services. Such a composition is a system of systems: independently operated and managed systems (airline, hotel chain, bank) that collaborate to deliver a capability none provides alone.

02Web services: SOAP building blocks

SOAP (formerly Simple Object Access Protocol, now just SOAP) is an XML-based protocol for exchanging messages, usually over HTTP. A SOAP message has four parts:

Envelope (required)

Root element marking the XML as a SOAP message.

Header (optional)

Security, transaction ID, routing info.

Body (required)

Actual request/response data.

Fault (optional)

Inside the Body; error code and message.

Services are described in WSDL (what operations exist, required) and listed in UDDI (directory). SOAP has built-in WS-Security, which is why banks and enterprises still use it despite its heaviness.

BasisRESTSOAP (RESTless example)
TypeArchitectural styleProtocol

InterfaceResources via URIsOperations via one endpoint
HTTP methodsGET, POST, PUT, DELETEMostly POST
DescriptionOpenAPI (optional)WSDL (required)

PerformanceFast, lightweightSlower, heavy XML
Used forWeb/mobile apps (GitHub, Maps APIs)Banking, enterprise systems

03REST: architecture style for distributed systems

REST (Roy Fielding, 2000) treats everything as a resource identified by a URI (e.g. /students/101); clients exchange representations, usually JSON, over HTTP.

REST constraints

  • Client-server - evolve independently.
  • Stateless - each request carries everything; server keeps no session.
  • Cacheable - responses can be cached.
  • Uniform interface - standard URIs + HTTP methods for every resource.
  • Layered system - proxies and load balancers can sit in between.
  • Code on demand (optional) - server may send executable code (JavaScript).
MethodOperationExample
GETReadGET /students/101
POSTCreate (not idempotent)POST /students
PUTFull replace (idempotent)PUT /students/101
PATCHPartial updatePATCH /students/101
DELETEDeleteDELETE /students/101

04Publish-subscribe model

In request-response, the consumer calls the provider directly. In publish-subscribe, publishers emit events to a broker/topic and subscribers receive only the topics they subscribed to - publishers and subscribers never address each other.

Publisher (provider)→ publishBroker / topic→ deliverSubscribers (consumers)
  • Decoupling: in time (subscriber offline still gets later messages), space (no addresses), and synchronization (async).
  • Example: flight-price service publishes fares/delhi-goa; the booking site, the alert app and analytics all subscribe independently.
  • Cloud tools: MQTT topics, Apache Kafka, AWS SNS and Azure Service Bus topics for pub-sub; SQS is point-to-point queueing, often paired as SNS → SQS.

05Basics of virtualization

A hypervisor (Virtual Machine Monitor) sits between hardware and operating systems, letting several VMs share one physical machine while each believes it owns the CPU, memory and devices. This is the foundation of resource pooling and elasticity.

Type 1 (bare-metal)Type 2 (hosted)
Runs onDirectly on hardwareOn a host OS
PerformanceNear-native, best isolationSlower (extra layer)
UseData centres, cloudLaptops, learning
ExamplesVMware ESXi, Hyper-V, KVM, XenVirtualBox, VMware Workstation

Containers vs VMs (asked often)

VMs virtualize hardware (each has a full guest OS, heavy, strong isolation). Containers virtualize the OS (share the host kernel, fast to start, weaker isolation). Cloud uses both: VMs for tenants, containers for microservices inside.

07Implementation levels of virtualization

Five levels, from lowest (closest to hardware) to highest. Lower levels give stronger isolation; higher levels are simpler.

LevelNameIdeaExample
1ISA levelEmulate the instruction set; run code for another CPUQEMU emulating ARM on x86
2Hardware abstraction (HAL)Hypervisor maps virtual hardware to physical (classic VMs)VMware, KVM, Xen
3Operating system levelIsolate processes into containers on one kernelDocker, LXC
4Library levelIntercept API calls (e.g. system calls) and redirectvCUDA, WSL 1 (Wine is often cited but is strictly API translation)
5Application levelApp runs in its own virtual machine (language VM)JVM, .NET CLR

08Virtualization structures, tools and mechanisms

Three things examiners mix up: structures (where the hypervisor sits: bare-metal Type 1, hosted Type 2), mechanisms (how privileged instructions are handled: trap-and-emulate, binary translation, hypercalls, hardware assist) and tools (ESXi, KVM, Xen, VirtualBox, Docker).

TechniqueIdeaTrade-off
Full virtualizationUnmodified guest; historically via binary translation rewriting sensitive instructions, today usually via hardware assistRuns any OS; near-native with VT-x/EPT
ParavirtualizationGuest modified to call hypervisor directly (hypercalls)Faster, needs modified OS (Xen)
Hardware-assistedCPU traps sensitive instructions (Intel VT-x, AMD-V)Fast, unmodified guest (KVM)
  • Memory: shadow page tables (hypervisor-maintained) vs EPT/NPT (CPU does two-level translation in hardware); ballooning reclaims idle memory; page sharing stores identical pages once.
  • I/O: full emulation (simple, slow) → para-virtual I/O (virtio frontend/backend, faster) → passthrough/SR-IOV (device assigned to VM, near-native).

09Virtualization of CPU, memory and I/O devices

1. CPU virtualization

Hypervisor gives each VM virtual CPUs (vCPUs) scheduled on real cores. Normal instructions run directly; privileged ones trap to the hypervisor via the three techniques above.

2. Memory virtualization

Two-level mapping: guest-virtual → guest-physical (guest OS) → host-machine address (hypervisor). Handled by shadow tables or EPT, plus ballooning and sharing for efficiency.

3. I/O virtualization

Many VMs share few NICs/disks: emulate in software, use virtio split drivers, or assign the device directly (SR-IOV shares one physical card as many virtual functions).

Memory trick for exams

CPU = trap-and-emulate · Memory = two-level mapping · I/O = emulate, paravirtualize, or passthrough.

10Virtualization support and disaster recovery

Disaster Recovery (DR) restores IT systems after hardware failure, cyber-attack, fire, flood or human error. Two numbers define every plan:

RTO

Recovery Time Objective: how quickly the service must be back up.

RPO

Recovery Point Objective: how much data (in time) can be lost - e.g. 15 min means backups at least every 15 min.

Cloud makes DR cheap because the standby site is rented, not owned. Virtualization helps directly: whole VMs (OS + app + data) are files that can be snapshotted, copied across regions and restarted in minutes.

Pattern (cheap → fast)Idea
Backup and restoreBackups in object storage; rebuild on failure (hours)
Pilot lightCore services always on, scaled up on demand (tens of minutes)
Warm standbyScaled-down copy always running; promote on failure (minutes)
Multi-site active-activeFull copies in two regions; near-zero RTO

Offered as DRaaS: AWS Elastic Disaster Recovery, Azure Site Recovery.

★Case studies & scenarios

Try each one on paper first, then open the model answer.

Case 1 · Travel site on SOA

Design a travel-booking site that combines flights, hotels and payments from different vendors. Show the SOA roles and choose SOAP or REST for each interaction.

Model answer

Roles: each vendor is a provider publishing WSDL/OpenAPI to a registry; the travel site is the consumer that finds, binds and invokes.

  • Flight/hotel search: REST + JSON (high volume, cacheable, mobile-friendly).
  • Payment: SOAP + WS-Security (strict contracts, built-in security, banking compliance).
  • Price alerts: publish-subscribe (providers publish fare topics; users and analytics subscribe independently).
Case 2 · Hypervisor choice

A data centre needs 200 production VMs with strong isolation; a student needs 3 Linux VMs on a Windows laptop for practice. Pick hypervisor types and justify.

Model answer
  • Data centre: Type 1 bare-metal (ESXi / Hyper-V / KVM) - runs on hardware, near-native speed, strong isolation, no host OS overhead.
  • Student laptop: Type 2 hosted (VirtualBox / Workstation) - runs as an app on Windows, easy install, slower but fine for learning.
Case 3 · Slow VM under load

A VM running a database is slow. The host has free CPU but memory is overcommitted. Explain the likely mechanism and two fixes using memory-virtualization tools.

Model answer

Likely memory pressure: two-level translation plus host swapping. Shadow/EPT overhead grows and the host pages to disk.

  • Enable ballooning to reclaim idle memory from other VMs.
  • Enable page sharing (identical OS pages stored once) and, long term, use EPT/NPT hardware and right-size the VM.
Case 4 · Bank RTO/RPO

A bank needs RTO < 5 minutes and RPO ≈ 0 after a region failure. Propose a DR pattern and explain how virtualization makes it possible.

Model answer

Use multi-site active-active: full copies in two regions with synchronous replication (RPO ≈ 0) and DNS failover (RTO in minutes). Cheaper options (backup/restore, pilot light) miss the 5-minute RTO.

Virtualization makes it practical: entire servers are VM images/snapshots that replicate and restart identically in the second region (DRaaS: Elastic Disaster Recovery / Site Recovery).

Case 5 · REST or SOAP?

Compare building a public mobile-app API vs a bank-to-bank fund-transfer interface. Which style fits each and why?

Model answer
  • Mobile API: RESTful - JSON, stateless, cacheable, uses GET/POST/PUT/DELETE, fast and simple.
  • Bank transfer: SOAP (a RESTless, operation-based protocol) - strict WSDL contract, XML-only, built-in WS-Security, can be stateful; heaviness is acceptable for correctness.
Answer template for any scenario
  1. One line: who provides, who consumes.
  2. SOA triangle or pub-sub sketch.
  3. REST vs SOAP choice with reasons.
  4. Virtualization level/type/mechanism involved.
  5. RTO/RPO and DR pattern if availability is asked.

11Quick revision (2-mark answers)

  • SOA: app built from independent reusable services; provider, registry, consumer.
  • System of systems: independently managed systems collaborating for a joint capability.
  • Features: loose coupling, reusability, interoperability, discoverability.
  • SOAP: XML protocol; Envelope, Header, Body, Fault; described by WSDL.
  • REST: resources via URIs, JSON over HTTP; stateless, cacheable, layered.
  • Methods: GET read, POST create, PUT full replace, PATCH partial update, DELETE delete.
  • Pub-Sub: publishers → broker/topic → subscribers; decoupled in time, space, sync (SNS, Kafka, MQTT; SQS is queueing).
  • Hypervisor: software mapping virtual CPU/memory/I-O to physical (VMM).
  • Type 1 / 2: bare-metal on hardware (ESXi) vs hosted on OS (VirtualBox).
  • Levels: ISA, HAL, OS (containers), library, application (JVM).
  • CPU: full (unmodified guest), para (hypercalls), hardware-assisted (VT-x).
  • Memory: guest-virtual → guest-physical → machine; shadow tables or EPT; ballooning, sharing.
  • I/O: emulation, virtio para-I/O, passthrough/SR-IOV.
  • VDI: desktops as central VMs; only pixels travel to endpoints.
  • RTO / RPO: how fast to recover / how much data loss allowed.
  • DR patterns: backup-restore, pilot light, warm standby, active-active.
